# Security: Secret Detection

This repository handles Hugging Face auth tokens and audio/data derived from
study participants, so it is set up to catch two kinds of accidental
disclosure before they reach GitHub:

1. **Credentials** (API keys, tokens, private keys) via a pre-commit hook
   running [detect-secrets](https://github.com/Yelp/detect-secrets).
2. **Organization-specific identifiers** (e.g. participant IDs) via a small
   local regex hook, since generic secret scanners have no way to know what
   your participant ID format looks like.

GitHub's own secret scanning (see [below](#github-secret-scanning)) is a
second, server-side layer that catches anything pushed anyway.

## How it works

### 1. detect-secrets (credentials)

[detect-secrets](https://github.com/Yelp/detect-secrets) scans staged file
contents with a set of plugins (AWS keys, private keys, JWTs, Slack/GitHub/
Stripe/etc. tokens, high-entropy strings that look like generic API keys...)
and blocks the commit if it finds a match that isn't already accounted for.

It was chosen over alternatives (e.g. `gitleaks`, `git-secrets`) because:
- It's pure Python, so it installs through the same `pip`/virtualenv workflow
  contributors already use for this project — no separate Go toolchain or
  binary download.
- It uses a **baseline file** (`.secrets.baseline`) instead of a blind
  allow/deny list. The baseline is a snapshot of everything detect-secrets
  currently flags in the repo (empty, as of this setup — see
  [Baseline audit](#baseline-audit) below), including a checksum per finding.
  New commits are only blocked for *new* findings not already in the
  baseline, which avoids the tool nagging about the same pre-existing
  false positive forever while still catching genuinely new secrets.
- Plugins run against staged content directly, so a secret is blocked
  *before* it is committed, not after.

### 2. Local participant ID check

`scripts/check_sensitive_patterns.py` is a small, local pre-commit hook
(no external dependency) that regex-matches staged file contents against
patterns your team defines. detect-secrets is built to recognize the *shape*
of credentials (base64/hex entropy, known token prefixes) — it has no
concept of what a participant ID looks like, so this gap needs an explicit,
editable rule.

**This ships with a placeholder pattern** (`[A-Z]{2,4}` + 3-6 digits, e.g.
`hv1023`, uppercased) since the real participant ID format wasn't available at setup
time. Before relying on this hook, edit `PARTICIPANT_ID_PATTERN` (and add
any other org-specific patterns to `SENSITIVE_PATTERNS`) in
[scripts/check_sensitive_patterns.py](scripts/check_sensitive_patterns.py)
to match your actual ID format. Sample/ground-truth data under
`sample_files/`, `ground_truth_files/`, and `data_dictionary/` is exempted
since it's de-identified and intentionally checked in.

### 3. check-added-large-files

Also included: a pre-commit-hooks check blocking new files over 50MB. This
isn't a secrets check, but full-length raw participant audio recordings are
themselves sensitive data, and this repo already ships de-identified sample
clips up to ~40MB — the limit is set above that so it only catches unusually
large accidental commits (e.g. a real recording dropped into the repo)
without blocking legitimate sample data.

## Installation (for contributors)

```sh
# from the repo root, with your project virtualenv active
pip install -e ".[dev]"     # installs pre-commit + detect-secrets
pre-commit install          # registers the git hook, one-time per clone
```

That's it — `git commit` will now run these checks automatically. To run
them on demand (e.g. against the whole repo, not just staged changes):

```sh
pre-commit run --all-files
```

### If a hook blocks your commit

- **detect-secrets** found something: if it's a real secret, remove it from
  the file (and rotate the credential if it was ever committed anywhere,
  even in history). If it's a false positive, add an inline comment
  `# pragma: allowlist secret` on that line, or re-run
  `detect-secrets scan --baseline .secrets.baseline` to update the baseline
  and commit the updated `.secrets.baseline`.
- **check-sensitive-patterns** found something: same idea — remove the real
  identifier, or adjust `SENSITIVE_PATTERNS`/`EXEMPT_PATHS` in
  `scripts/check_sensitive_patterns.py` if it's a false positive.

### Baseline audit

`.secrets.baseline` was generated by running a full-repo scan
(`detect-secrets scan`) as part of this setup, which doubled as an audit of
existing history for already-committed secrets. Result: **no findings** —
`"results": {}` in the baseline. (This scans tracked file *contents* at
HEAD; if you want to check the full commit history for secrets that were
later removed, see [Auditing git history](#auditing-git-history) below.)

## GitHub Secret Scanning

GitHub runs its own [secret scanning](https://docs.github.com/en/code-security/secret-scanning)
against pushed content, independent of the local pre-commit hooks above —
useful as a backstop for anyone who commits without the hooks installed
(e.g. edits made directly on GitHub.com, or contributors who skip setup).

- **Default patterns + push protection are free for all public repositories**
  and require no configuration — GitHub already scans pushes to this repo
  for known credential formats (cloud provider keys, common API tokens,
  etc.) and can block a push containing one before it's ever stored.
  Verify/adjust this under **Settings → Code security → Secret scanning**
  in the GitHub repo.
- **Custom patterns** (e.g. a regex for your participant ID format,
  enforced server-side in addition to the local hook) are part of GitHub
  Advanced Security / Secret Protection, which is generally available to
  organization-owned repos with that add-on enabled — it is not guaranteed
  to be available on every plan for public repos. If your GitHub
  organization has it enabled, custom patterns can be added at
  **Settings → Code security → Secret scanning → Custom patterns**, using
  the same regex you configure in
  `scripts/check_sensitive_patterns.py`. If not available, the local hook
  in this repo is the enforcement mechanism for that pattern today.

Since repo-level GitHub settings affect a shared, org-owned repository, they
weren't changed as part of this setup — enabling/adjusting them is left to
someone with admin access to the repo, per the guidance above.

## Auditing git history

The baseline scan above only covers the current state of tracked files. To
check whether a secret was committed and later removed (still present in
history), run detect-secrets against the full git history:

```sh
pip install detect-secrets
detect-secrets scan --all-files
# or, for deeper history auditing:
git log -p | detect-secrets scan --string
```

If a real secret turns up in history, rotating the credential is required —
removing it from a future commit does not remove it from history that's
already been pushed (see GitHub's
[guide on removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)).
